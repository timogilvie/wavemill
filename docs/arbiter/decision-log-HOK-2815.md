# Decision Log Entry - HOK-2815

Date: 2026-09-24 America/New_York

Entry:

**2026-09-24 · HOK-2815 · wavemill → arbiter / native challenge program** — Arbiter R6 reconnaissance ships as a standalone analysis script (`tools/arbiter-r6-analysis.ts`) that reads `.wavemill/evals/evals.jsonl` and `.wavemill/evals/challenge-records.jsonl` in a single streaming pass and emits a markdown report to stdout. The report answers the two R6 questions the Arbiter program brief posed: (1) does net pair yield rise or fall after the reviewer-stage `challenge.fork()` cut over, and (2) is the native launch funnel healthy enough to justify carrying the fork mechanism into coder-stage arms. The pre/post fork comparison partitions comparison records at an operator-supplied `--fork-date` cutoff, then reports pairs launched, pairs reaching comparison, delivery-comparison yield, and every non-comparison cause with counts and rates. A simulated usable-forfeits column measures the fault-tolerance the shared-prefix design gives up: pre-fork primary hard failures that would have shipped code independently under the old two-arm regime. The native launch funnel walks pairs through eligible → selected → intent persisted → arm materialized → stage launched → terminal → valid comparison, with drop-off and cumulative yield at every step and average cost/time on the valid-comparison rows. Provider and canonical-model strata surface where the funnel is bleeding, and `--stratify-by-prefix` splits the post-fork period into forked vs independent pairs. The Go/No-Go recommendation is data-driven: `Go` when post-fork yield lifts by ≥ 5 pp and forked pairs match independent pairs, `No-Go` when yield regresses by ≥ 5 pp or forked pairs trail independent pairs by ≥ 5 pp, and `Insufficient Data` when fewer than 20 post-fork pairs have accrued; the middle ground defaults to `No-Go` because the coder-stage fork gives up more fault tolerance than the reviewer-stage fork, so a null result is not a green light. The recommendation this branch ships is therefore **operator-run** — the script must be executed against the current corpus (`npx tsx tools/arbiter-r6-analysis.ts --stratify-by-prefix > report.md`) and the resulting `Recommendation` block copied into `docs/arbiter/arbiter-program-brief-and-decision-log-0e9fa05622a1` before Phase 2.4 authorizes coder-stage `challenge.fork()` work. The `challenge.rate` config remains unchanged during the measurement window.

Immediate effects:

- `tools/arbiter-r6-analysis.ts` is available for on-demand reconnaissance and is registered as a supported unit test in `tests/run-unit-tests.sh`.
- Extending `challenge.fork()` to coder-stage arms remains gated on running the analysis against post-cutover data and pasting the resulting `Recommendation` line and justification into the Arbiter Program Decision Log (`docs/arbiter/arbiter-program-brief-and-decision-log-0e9fa05622a1`).
- No production config or infrastructure is changed by this task; the script is read-only and does not mutate eval or comparison stores.
- Rollback is a straightforward revert of this commit; the analysis output is not consumed by any other subsystem.
