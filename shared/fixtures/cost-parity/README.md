# Cost Parity Corpus

This directory contains a **migration oracle** for replacing Wavemill's legacy cost engine (`shared/lib/workflow-cost.ts`) with the Hokusai SDK's cost engine.

## Overview

The corpus consists of:

- **`manifest.json`** — Input specification: 15 synthetic test cases covering different scenarios (Claude Code, Codex, native Pi, mixed models, caching, provider costs, etc.)
- **`baseline.json`** — Ground truth output from the current (legacy) engine, generated by `npx tsx tools/cost-parity.ts --write`
- **`schema.ts`** — Type definitions and validation for the manifest
- **`consumer-inventory.json`** — Machine-readable inventory of all files that import `workflow-cost.ts`, classified by type (measurement, pricing policy, report, backfill, etc.)

## Privacy

All session files in `manifest.json` are **synthetic** and **privacy-safe**:

- No real transcript text is stored
- Usage metrics are numeric only
- A `"secret-token-should-not-persist"` canary appears in structured fields to catch leaks
- The baseline stripping sanitizes all paths and canaries before storage

## Running the Harness

### Generate or regenerate the baseline

After modifying the legacy cost engine, regenerate the baseline:

```bash
npx tsx tools/cost-parity.ts --write
git diff shared/fixtures/cost-parity/baseline.json  # review changes
```

This is deterministic — running it twice produces identical output. If it doesn't, investigate the nondeterminism before committing.

### Regression test (default)

Compare the current engine against the stored baseline:

```bash
npx tsx tools/cost-parity.ts
# Exit code 0 if all tests pass, 1 if differences found, 2 for corpus errors
```

### Inspect a single case

```bash
npx tsx tools/cost-parity.ts --case claude-mixed-one-unpriced
```

### JSON output

```bash
npx tsx tools/cost-parity.ts --json | jq '.'
```

## Legacy Defects (Expected Fixes)

These are documented in `docs/cost-engine-migration-oracle.md` under "Legacy Behavior and Expected Fixes". Each defect has:

- **ID** (EF-1, EF-2, ..., EF-12)
- **Impact** — which downstream consumers are affected
- **Current behavior** — what the legacy engine does
- **Proposed fix** — what the SDK should do instead

Examples:

- **EF-1**: Partial totals presented as complete (unpriced models add 0 to total, but downstream treats it as the real total)
- **EF-2**: Claude Code usage double-counted (same message id repeated, each line summed)
- **EF-3**: Codex cached and reasoning tokens double-charged

## Integration: HOK-3075 and HOK-3076

The SDK bridge (_not in this PR_) will:

1. Implement a `SdkCostEngine` compatible with the harness's `CostEngine` interface
2. Plug it into the same comparator: `npx tsx tools/cost-parity.ts --mode migration --engine sdk`
3. Classify differences as strict violations or expected fixes per case
4. Document any additional cross-repo issues (e.g., EF-3 is also in hokusai-sdk's Codex parser)

When migration mode reports all differences as either "stale_expected_fix", "expected_fix_applied", or "expected_fix_wrong_value" on SDK-bridged cases, the SDK engine is ready to replace the legacy one.

## Validation Tests

All harness behavior is tested in `shared/lib/cost-parity.test.ts`:

- Manifest validation (unique ids, known tags, schema integrity)
- Legacy engine reproduces baseline exactly
- Comparator detects mutations
- Expected fixes apply correctly in migration mode
- USD tolerance (1e-9)
- Privacy canaries are stripped
- Environment cleanup on error
- Mirror test: harness output matches `collectExecutionEconomics`
- Inventory guard: new imports to workflow-cost.ts must be classified

Run with:

```bash
node --test shared/lib/cost-parity.test.ts
```
